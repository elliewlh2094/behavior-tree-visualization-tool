# Todo: Behavior Tree Visualization Tool — v1.7.1 "Unified History Timeline"

> Supersedes v1.7's dual-stack model. v1.7 commits stay as the historical record of the dual-stack attempt; v1.7.1 replaces the runtime model.
> Legend: `[ ]` not started · `[~]` in progress · `[x]` done · 🛑 = checkpoint (requires human approval to pass)

## Objective

v1.7 closed F19 at the cross-tree-action layer but smoke testing on 2026-05-10 surfaced three structural defects in the dual-stack (per-tree + global, merged by `historySeq`) approach:

1. **UI-layer** — `undo` blindly restores `activeTreeId` from the snapshot (decision 7), so renaming Tree 2 from its tab and clicking back to Main teleports the user to Tree 2 on Ctrl+Z. Tab switching is not an undoable action.
2. **Algorithm-layer** — the merge picks max-seq between the *active tab's* local stack and the global stack. Switching tabs changes which local stack is consulted, so a per-tree action made on a different tab can be skipped over even though it is chronologically more recent.
3. **Data-model** — after a global pop restores the whole document to an earlier state, per-tree stacks can still hold entries whose snapshots reference an earlier version of trees that the global pop already rewound past. Popping them is a visual no-op while leaving the Undo button enabled, and a subsequent redo can resurrect a stale forward branch.

v1.7.1 replaces the dual-stack with a **single timeline of document-level snapshots**. Tabs are pure UI projection over that timeline. Undo always reverts the chronologically-most-recent action regardless of which tab is active; tab switching never affects the order of history operations.

## Resolved Spec Decisions

| # | Question | Decision |
|---|---|---|
| 1 | **Architecture** | **Single unified stack.** Replace v1.7's `undoStacks` / `redoStacks` (per-tree) + `globalUndoStack` / `globalRedoStack` (doc-level) + `historySeq` with one `undoStack: RingBuffer<DocSnapshot>` and one `redoStack: RingBuffer<DocSnapshot>`. `DocSnapshot = { document: BTDocument; activeTreeId: string }`. No seq counter — single stack has natural ordering. |
| 2 | **Push helper** | Single `withSnapshot(state, patch)` replaces `withHistory`, `withCrossTreeHistory`, and the inline `beginGesture` push. Every action that pushes to history calls it. Identity short-circuits stay in callers. |
| 3 | **Active tab on undo/redo** | Restore `activeTreeId` from the snapshot **only if the current `state.activeTreeId` is no longer present in the restored document**. Otherwise leave the user where they are. This is the only legitimate teleport case (e.g., undoing an `addTree` while you are on the new tab). For every other case undo/redo never moves the displayed tab. Replaces v1.7 decisions 3 and 7 (which conflicted). |
| 4 | **Snapshot shape** | Full `BTDocument` per snapshot. Memory cost is bounded by `HISTORY_CAPACITY=10` envelopes; untouched `BTTreeDef` objects retain reference identity through immutable updates, so snapshots share most tree references in practice. |
| 5 | **Redo invalidation** | Any push to `undoStack` clears `redoStack` entirely. Single stack — no merge cases, no per-tree carve-outs. |
| 6 | **Eviction** | One `RingBuffer<DocSnapshot>` of capacity `HISTORY_CAPACITY` per direction. Oldest entry across the whole document falls off when full. Replaces v1.7 decision 4 (independent ring buffers per tree + global). |
| 7 | **Selection on undo/redo** | Cleared on every history op (preserves v1.7 decision 6). |
| 8 | **Per-tree state cleanup on `deleteTree`** | Same as v1.7 decision 8: do not drop per-tree state on delete. Viewport is the only remaining per-tree state; it survives so undoing a delete restores both content and viewport. |

## Out of Scope

- Same exclusions as v1.7: undoing `setDocument` / `setActiveTreeId`, undoing preference changes, new cross-tree action types.
- Migration of pre-existing user state — there is no persisted history; every browser reload starts with empty stacks.

## T2 — Rewrite `undo` / `redo` with `stillExists` fallback

**Description:** Replace v1.7's max-seq merge logic with a single-pop-per-call implementation. On undo: `peek` then `pop` from `undoStack`; restore `document` from the snapshot; set `activeTreeId` to current value if it still exists in the restored doc, else fall back to the snapshot's. Push the pre-restore state (current `document` + `activeTreeId`) onto `redoStack`. Clear selection. Redo is symmetric (swap stacks).

**Acceptance criteria:**
- [ ] `undo` and `redo` operate on the unified stacks.
- [ ] `stillExists` rule implemented and unit-tested in T4.
- [ ] Selection cleared on every history op.
- [ ] No-op when the source stack is empty (`return {}` like v1.7).

**Dependencies:** T1.

**Files:** `src/store/bt-store.ts`.

**Estimated scope:** S.

## T5 — New 3-tab interleaved e2e test

**Description:** Add a test in `e2e/multi-tree.spec.ts` exercising the user's stated test conditions. Three tabs, interleaved per-tree and cross-tree actions, verified for both undo and redo, with and without tab-switching between presses.

**Acceptance criteria:** Six assertion blocks executed sequentially in one test:
- [ ] **(1) Undo full reversal** — Ctrl+Z × N reverts in exact reverse-chronological order.
- [ ] **(2) Redo full replay** — Ctrl+Y × N replays in exact chronological order.
- [ ] **(3) Tab-switch invariance for undo** — re-run scenario; switch tab before each Ctrl+Z; assert post-undo doc matches step (1) at every step (only `activeTreeId` may differ, and only because of the manual switch).
- [ ] **(4) Tab-switch invariance for redo** — same as (3) but for Ctrl+Y vs (2).
- [ ] **(5) Round-trip identity** — Ctrl+Z × N then Ctrl+Y × N produces a doc byte-identical to post-Step-N.
- [ ] **(6) Active-tab fallback rule** — undoing `addTree` while on the new tab moves active back to the snapshot's `activeTreeId`; undoing it from a surviving tab does not move active.
- [ ] User's reported 5-action scenario is included verbatim in the fixture so the exact reported case is regression-locked.
- [ ] `npm run test:e2e` green.
