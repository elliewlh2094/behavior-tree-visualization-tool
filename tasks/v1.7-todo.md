## Objective

Close the cross-tree-mutation undo gap surfaced by v1.4 smoke testing (2026-05-08): renaming a SubTree, calling `addTree`, or `deleteTree` is currently skipped from history (`// No history snapshot — same F19 deferral as renameTree/addTree`). After a `renameTree`+`undo` the renamed tree's `name` and tab label revert correctly only because per-tree history happened to snapshot the SubTree node — but the *referenced* tree definition stays renamed, leaving an inconsistent state. v1.7 makes all three actions undoable atomically.

## Resolved Spec Decisions

| # | Question | Decision |
|---|---|---|
| 1 | **Architecture** | **Approach B — global stack + monotonic seq.** Per-tree stacks remain `RingBuffer<{seq, tree: BTTreeDef}>` (item type widened from raw `BTTreeDef`). Document-level mutations push `{seq, document: BTDocument}` to a separate `globalUndoStack: RingBuffer<{seq, document}>`. Undo on any tree picks `max(local-stack-top, global-stack-top)` by seq. Redo symmetric. |
| 2 | **Affected actions** | `renameTree`, `addTree`, `deleteTree`. All three currently `// No history snapshot`. |
| 3 | **Undo semantic when global is most recent** | Undo on tree A pops the global snapshot regardless of which tab made the action. Restoring a doc-snapshot replaces `state.document` wholesale (resets *all* trees). Active tab does not switch — the user stays where they were and the affected tab(s) update underneath. |
| 4 | **Eviction** | Per-tree stack and global stack use independent `RingBuffer<…>` of capacity `HISTORY_CAPACITY`. No global ordering invariant required: when one is empty, just pop the other; when both have entries, compare seqs. An evicted entry is simply not pop-able anymore — there is no orphan-link bookkeeping (this is why Approach A was rejected). |
| 5 | **Redo invalidation** | Any *new* push to either undo stack (per-tree or global) clears *both* redo stacks. Otherwise a tree-local redo could resurrect a stale doc snapshot, or vice versa. This is stricter than today's "clear redo for the active tree only" — accept the broadening because cross-tree pushes have legitimately invalidated the entire forward branch. |
| 6 | **Selection on global undo** | Cleared (matches today's `undo`/`redo` behavior). The active tree may not even contain the previously-selected nodes after a doc-restore, so clearing is the safe default. |
| 7 | **Active tree on `deleteTree` undo** | When `deleteTree` is undone, the restored document contains the tree again, but `activeTreeId` should also be restored to the value at push-time (so the tab the user deleted comes back active). Snapshot stores `{seq, document, activeTreeIdAtPush}` for `deleteTree` specifically, or — simpler — the global snapshot always carries `activeTreeId` alongside `document` and undo restores both. **Decision: snapshot is `{seq, document, activeTreeId}`** to keep the shape uniform across all three actions. |
| 8 | **Per-tree state cleanup on `deleteTree`** | Today's `deleteTree` calls `dropTreeState(state, treeId)` (drops undo/redo/viewport for that treeId). With v1.7, that drop is now *destructive* if the user later undoes the delete: their per-tree undo history for the deleted tree is gone. **Decision: defer per-tree-state cleanup** — `deleteTree` no longer drops per-tree state at action time. The state hangs around as a small leak. If the user explicitly does *not* want to undo (e.g., redo of something else), the state will be cleared the next time the deleted tree's id is reused (never, since uuids) or on file load (`setDocument` resets all stacks). Acceptable trade-off for correctness. |

## Out of Scope

- Undoing `setDocument` (file open) — explicitly resets history; documented behavior.
- Undoing `setActiveTreeId` (tab switch) — pure UI state, never has been undoable.
- Undoing preference changes (Settings panel) — different store with `persist` middleware (AD1), no history.
- Redo of `addTree` after un-doing it: the tree's per-tree state was *not* dropped (decision 8), but the new uuid means it won't collide with anything. No special handling needed.
- New cross-tree actions beyond the existing three (e.g., reordering tabs, moving a node between trees) — out of scope for F19; if/when added they call `withCrossTreeHistory` like the others.

## T3 — `undo` / `redo` merge per-tree + global by max-seq ✅ Done (2026-05-09)

**Description:** Wire the global stack into `undo` and `redo`. The fix lands here.

**Algorithm (undo):**
1. Read `localTop = peek(undoStacks[activeTreeId])` (may be `undefined`).
2. Read `globalTop = peek(globalUndoStack)` (may be `undefined`).
3. If both undefined → no-op.
4. If only one defined → pop that one, restore accordingly.
5. If both defined → pop whichever has higher `seq`.
   - **Local pop:** restore the tree (current behavior), push current active tree onto `redoStacks[activeTreeId]` with a *fresh* seq from `historySeq + 1` (so a redo→undo sequence preserves chronological ordering relative to other actions). Increment `historySeq`.
   - **Global pop:** replace `state.document` and `state.activeTreeId` with the snapshot's. Push `{seq: historySeq+1, document: prevDocument, activeTreeId: prevActiveTreeId}` onto `globalRedoStack`. Increment `historySeq`. Clear selection.
6. **Critical:** local-pop also clears `globalRedoStack`? **No** — undo is *not* a new action, it's a step backward. Only *new* pushes (real user actions via `withHistory` / `withCrossTreeHistory`) clear redo stacks. Undo just shuffles between undo and redo stacks. Same as today's per-tree behavior.

**Redo:** symmetric — `redo` pops max-seq between `redoStacks[activeTreeId]` and `globalRedoStack`, restores, and pushes onto the corresponding undo stack.

**Acceptance criteria:**
- [x] `undo` implements the max-seq merge above. Local-pop path is byte-identical to today's behavior modulo the seq tag.
- [x] `redo` implements the symmetric merge.
- [x] When the global stack is empty (the v1.4 baseline scenario), behavior is unchanged from v1.4 — verified by all existing tests passing.
- [x] When `globalTop.seq > localTop.seq`, undo restores the document snapshot, replaces `activeTreeId`, clears selection.
- [x] Selection cleared on every undo/redo (matches today).
- [x] No re-tagging quirks: undo→redo→undo on a single per-tree action returns to the same state (round-trip property formalized in T4 tests).

**Verification:**

- [x] `npm run test:ci` green — 359/359 (existing T2-augmented suite still passes; T4 will add the merged-undo/redo coverage).
- [x] `npm run test:e2e` green — 30/30. The e2e in T5 will cover the cross-tree-undo user-visible flow.

## SUPERSEDED 2026-05-10 — see `tasks/v1.7.1-todo.md`

Smoke testing on 2026-05-10 surfaced three structural defects in v1.7's dual-stack approach:

1. **UI-layer** — undo blindly restored `activeTreeId` from the snapshot (decision 7), teleporting users to a tab they had since clicked away from. Tab switching is not an undoable action; it should not be re-played by undo.
2. **Algorithm-layer** — the merge picked max-seq between *the active tab's* local stack and the global stack. Switching tabs changed which local stack was consulted, so a per-tree action made on a different tab could be skipped over even though it was chronologically more recent.
3. **Data-model** — after a global pop restored the whole document to an earlier state, per-tree stacks could still hold entries whose snapshots referenced trees the global pop had already rewound past. Popping them was a visual no-op while leaving the Undo button enabled, and a subsequent redo could resurrect a stale forward branch.

v1.7.1 replaces the dual-stack with a **single timeline of document-level snapshots**. Tabs are pure UI projection. Undo always reverts the chronologically-most-recent action regardless of active tab; tab switching never affects history operation order. Decisions 3 and 7 from this spec are obsolete (the active-tab fallback rule replaces both). Decisions 5, 6, 8 are retained in v1.7.1's contract.

v1.7's commits stay as the historical record of the dual-stack attempt. v1.7.1 is the live runtime model.
